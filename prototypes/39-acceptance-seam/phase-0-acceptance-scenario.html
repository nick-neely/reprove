Proposed answer

What this prototype claims the scenario should be, and what it found on the way.

One spine, ten walkthroughs

“A single scenario” cannot mean one linear walk, because accepting a Result terminalizes the Run it was accepted into, and every rejection needs a Run that has not yet terminalized. What is single is the spine — signed delivery, Run creation, lifecycle scheduling, claim — and the nine other cases fork off it at defined points, through the same seam, against the same database, in one harness.

One case costs something, and the cost is worth naming. The hosted start() orphan cannot be reached by a Worker behaving badly, because the crash is in Reprove’s own dispatch path between start() and markExecuting. Reaching it needs an injection point at the composition seam — a test-only branch inside shipped orchestration. That is a genuine cost, and it is paid because ADR 0015 names this window as the hole that widened #41 from executing to Acceptance’s whole eligibility window. A scenario that skipped it would not exercise what #39 inherited. The self-hosted-silence case is kept alongside it, at no cost, because two placements reaching one transition on one shared predicate is what shows the window is placement-neutral.

What the scenario observes externally

  • Webhook route status and body for a valid signature, a tampered one, and an oversized body.
  • The intercepted GitHub request shape: App JWT, installation token, GET /repos/…/pulls/42.
  • Claim endpoint status and body, for both placements.
  • Result endpoint status and the named rejection, for every reachable rejection.
  • Two concurrent Result submissions: exactly one 200, one 409 not_eligible.
  • A Run left at claimed with a null pass id by a hosted start() orphan, terminalized by liveness alone.
  • The run row read back under withOwner(): status, token, acceptedAt, failure detail.
  • The ingress ledger row’s terminal state and disposition.
  • The build gate’s own assertions: no external module in the workflow bundle, pg in the output trace, the app boots.

What stays absent, and is asserted absent

  • No checkout, no Workspace, no Sandbox, no Harness. The Result is a fixture.
  • No Review published, no Comment, no Reconciliation, no Threshold or Ignore.
  • No Check run — ADR 0013 removed it from Phase 0.
  • No Refusal path — ADR 0013 makes none reachable.
  • No Enrollment and no Lease renewal transport.
  • No progress messages and no cancellation delivery.
  • No narrative supplied to any Reviewer, so ADR 0013’s inherited constraint stays inherited.

Three findings this prototype produced

wrong_tenant is unreachable from inside the boundary

Acceptance re-probes the Run to name its rejection. That probe runs under withOwner(), so a Run belonging to another Owner is not merely ineligible — it is invisible. The probe returns nothing, and the only answer available from inside the boundary is unknown_run.

Reaching wrong_tenant would mean probing with withoutOwner(), punching through the tenancy boundary to produce a more specific error message. There is a real argument on the other side: ADR 0014 named this rejection deliberately, on the grounds that “rejected” alone cannot distinguish a superseded Run from a forged tenant, and that the distinction is what makes the boundary auditable.

This prototype does not settle it. Dropping wrong_tenant amends ADR 0014's rejection set, and moving it to the authentication layer relocates an auditability guarantee rather than preserving it. What the prototype establishes is only that the current design cannot deliver it from Acceptance. The choice is the first Human verdict below.

livenessFor has no home, and needs one

ADR 0015 fixes executionExpiresAt = claimedAt + livenessFor but never says where livenessFor is configured. Left unplaced it lands inline in the claim path, which is exactly the hazard ADR 0013 created Phase0RunProfile to prevent: a Phase 0 fixture silently becoming product policy.

It joins Phase0RunProfile beside the claimable-deadline policy. The scenario then runs the real lifecycle loop, the real durable sleep and the real conditional UPDATE, with only the two numbers moved.

The re-probe’s disambiguation order is backwards in #38

Found by running the “Token rotation is not the boundary” walkthrough. #38’s acceptResult names its rejection by re-probing and testing the token before falling through to not_eligible. So a stale token submitted against a Run that worker_lost has already terminalized reports execution_mismatch — a rotated token — when the Run’s actual problem is that it ended.

ADR 0015 requires the opposite: terminal state is the stronger and clearer fact, so the eligibility half of the predicate must be disambiguated first and token identity second. This is a one-line reordering, and without the scenario nothing would have caught it: both orders return a rejection, both look correct, and only the name differs.

Where it runs

The scenario is the payload of the real-builder CI check ADR 0014 already mandates, not a second gate. That check builds from clean, asserts the workflow bundle and the output trace, then starts the built application — which is precisely the fixture this scenario needs. Its database is local Postgres 17 behind PgBouncer, as #37 chose: the invariants under test are standard Postgres, RLS and transaction-pooling behaviour, so keeping them local makes the Phase 0 exit deterministic, offline and secret-free. Neon remains the production target, and Neon deployment compatibility is a separate production check rather than part of this canonical scenario.
