Throwaway prototype for Prove the local broker-capable Sandbox contract

Execution begins only after the box proves itself

Drive a Docker or Podman Sandbox through capability probing, per-instance attestation, dispatch, and verified teardown. The prototype tests whether these seams are enough to make every hard-property loss an explicit Refusal before repository code runs.

Question under test

Proposal: split evidence into a cached host capability probe and a fresh attestation of the exact Sandbox instance. @reprove/sandbox-container owns both and exposes an attested HarnessV1SandboxProvider. @reprove/worker-core alone turns the attestation plus Run facts into authorization or a protocol Refusal. No Harness process starts before authorization.

Assumption to challenge: runtime configuration and inspect output are not enough. Each hard property also gets an adversarial canary from inside the created Sandbox, and cleanup gets a separate post-stop proof.

1. Capability probe

Fingerprint the provider build, runtime daemon, kernel, and cgroup mode. Establish what this host can create, not what one Sandbox currently enforces.

@reprove/sandbox-container
2. Instance attestation

Create one labeled Sandbox, inspect it outside, run canaries inside, and return closed check records tied to its instance id.

@reprove/sandbox-container
3. Eligibility gate

Combine attested Isolation with Exposure and Provenance. A failed hard check or ineligible cell produces a structured Refusal.

@reprove/worker-core
4. Harness provider

Expose ports, network policy, restricted handles, and request transformations. The credential callback rejects every real secret.

Guided walkthroughs

      
Each tab resets to a known fixture. Press its steps in order and watch where authority is withheld.

      

        
        
        
        
      


      

        
Rootless Docker establishes the whole contract

        
The host probe earns only a capability claim. The created instance must still pass every canary before Worker core authorizes execution. Teardown is part of the observable outcome.

        

      


      

        
Rootful Docker is a Sandbox, but not for an account credential

        
All hard properties pass and Isolation computes to container. Worker core then refuses the account + container combination before execution. Rootful is a strength fact, not a fake hard-property failure.

        

      


      

        
The brokering regression cannot warn and continue

        
The provider supports request transformations, but the Adapter credential callback observes a non-placeholder value. That is direct proof of the feared silent downgrade, so attestation refuses and execution stays impossible.

        

      


      

        
A teardown call is not teardown proof

        
The Pass finishes, then destroy leaves a labeled network behind. The completed candidate Result cannot turn cleanup failure into success. Worker core reports Failure and quarantines the capability fingerprint until cleanup succeeds.

        

      

    


    

      

        
Host capability probe

        

          
Cache only against a fingerprint that changes with every relevant artifact.

          
    
            
  • Provider build digest and probe schema version
    • 
            
  • Runtime kind, client and server versions, and rootless fact
    • 
            
  • Kernel, cgroup version, seccomp availability, and network backend
    • 
            
  • Support for ports, request transformations, and restricted handles
    • 
          

        

      

      

        
Fresh instance attestation

        

          
Bind every record to the created instance id and probe fingerprint.

          
    
            
  • Inspect: unprivileged, minimal caps, seccomp, limits, mounts, labels
    • 
            
  • Inside canaries: namespace ids, no socket, no host sentinel or authority, protected inputs
    • 
            
  • Network canaries: direct traffic denied, allowed proxy path works, all unmatched requests fail
    • 
            
  • Broker canary: only a random placeholder is visible inside; transform occurs outside
    • 
          

        

      

      

        
Adversarial contract tests

        

          
Run the same black-box suite against Docker rootless, Docker rootful, and Podman rootless.

          
    
            
  • Try to reach the runtime socket, host sentinel, and disallowed network targets
    • 
            
  • Try to read the real provider credential from env, files, process data, and echoed headers
    • 
            
  • Try fork, memory, CPU, and wall-clock limits
    • 
            
  • Kill and cancel at each lifecycle edge, then assert no labeled container, network, or volume remains
    • 
          

        

      

      

        
Runtime evidence adapters

        

          
Docker and Podman normalize different command output into the same closed check records.

          
    
            
  • Host: docker info or podman info --format json
    • 
            
  • Outside: inspect the exact id and retain only bounded security facts
    • 
            
  • Inside: exec the same versioned canary image and collect closed pass or fail codes
    • 
            
  • Cleanup: list containers, networks, and volumes by immutable Reprove label and require an empty set
    •
